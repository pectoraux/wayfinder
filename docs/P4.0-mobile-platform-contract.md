## 4. Authentication Architecture Options

### Option A: Reuse NextAuth JWT cookie

- **Mechanism**: Android WebView stores the NextAuth session cookie
- **Pros**: No new code
- **Cons**: WebView is not native; cookie storage on Android is fragile; no token revocation; no refresh; not idiomatic for mobile

### Option B: Long-lived Bearer token

- **Mechanism**: Single API token stored in Android Keystore
- **Pros**: Simple
- **Cons**: No expiry → stolen token is permanent; no rotation; no revocation without a blocklist; violates the directive's security requirements

### Option C: Short-lived access token + rotating refresh token

- **Mechanism**:
  - `POST /api/auth/credentials` → `{ accessToken (15min), refreshToken (30d) }`
  - `POST /api/auth/refresh` → `{ accessToken }`
  - `POST /api/auth/logout` → revokes refresh token
  - Refresh tokens rotate on each use (refresh token rotation)
  - Access token is a signed JWT (stateless verification)
  - Refresh tokens are stored in DB (revocable)
- **Pros**: Standard mobile auth; revocable; rotation limits replay window; stateless access token verification
- **Cons**: New endpoint + DB table for refresh tokens; more complex than cookie

### Option D: OAuth2 / OIDC provider (Auth0, Cognito, etc.)

- **Pros**: Managed; battle-tested
- **Cons**: External dependency; cost; overkill for current scale

## 5. Selected Authentication Architecture + Rationale

**Selected: Option C — Short-lived access token + rotating refresh token**

### Rationale

1. **Idiomatic for mobile.** Native Android apps use token-based auth, not browser cookies. OkHttp/Retrofit interceptors naturally attach `Authorization: Bearer <token>`.

2. **Revocable.** Refresh tokens are stored in the DB (`MobileSession` table — to be added to Prisma schema). Logout revokes the token immediately. A compromised token expires in 15 minutes.

3. **Rotation limits replay.** Each refresh produces a new refresh token and invalidates the old one. A stolen refresh token has a single-use window.

4. **Stateless access verification.** The access token is a signed JWT. The server verifies it without a DB lookup on every request (only refresh requires DB). This is critical for Vercel serverless — no DB hit on every API call.

5. **Doesn't break the web client.** The existing NextAuth cookie flow remains untouched. The new token flow is additive — a new `CredentialsProvider` variant or a dedicated `/api/auth/mobile/*` endpoint set.

6. **No external dependency.** No Auth0/Cognito cost. Uses the existing bcrypt password verification + a new JWT signing key.

### Token design

```
Access token (JWT, 15 min):
  Header: { alg: "HS256", typ: "JWT" }
  Payload: {
    sub: userId,
    role: "USER" | "ADMIN" | "DEMO",
    deviceId: string | null,
    iat: timestamp,
    exp: timestamp (iat + 900)
  }
  Signed with: MOBILE_JWT_SECRET (env var, separate from NEXTAUTH_SECRET)

Refresh token (opaque, 30 days):
  - Random 32-byte hex string
  - Stored in MobileSession table: { id, userId, tokenHash, deviceId, createdAt, expiresAt, revokedAt }
  - Hashed at rest (bcrypt or SHA-256)
  - Rotated on each /api/auth/refresh call
```

### New Prisma model (to be added in P4.0 implementation)

```prisma
model MobileSession {
  id          String    @id @default(cuid())
  userId      String
  tokenHash   String    @unique  // bcrypt hash of the refresh token
  deviceId    String?
  createdAt   DateTime  @default(now())
  expiresAt   DateTime
  revokedAt   DateTime?
  lastUsedAt  DateTime?

  @@index([userId])
  @@index([expiresAt])
}
```

## 6. Authorization Model

### Per-request authorization chain

```
1. Extract Authorization: Bearer <accessToken> header
2. Verify JWT signature + expiry
3. Extract userId from JWT sub
4. For resource-specific requests:
   a. Load the resource (DecisionRecord, ActionOutcome, etc.)
   b. Verify resource.userId === authenticated userId
   c. If mismatch → 404 (not 403, to avoid leaking existence)
5. For objective-scoped requests:
   a. Verify the resource's objectiveId matches the user's objective
   b. Cross-objective access is allowed for read (history) but not write
```

### Client must NEVER submit

- `userId` (server derives from JWT)
- `objectiveId` as authorization (server derives from resource ownership)
- `strategySnapshot` (server resolves from DecisionRecord)
- `predictedEffect`, `predictedCostUSD`, etc. (server derives from historical strategy)
- `outcomeType` (server inherits from expected outcome)
- `provenance` claiming `EXTERNAL_VERIFICATION` (server rejects from clients)
- `evaluationStatus` (server computes deterministically)

### Server derives authority

Every mobile API request that touches a resource:
1. Authenticates the user from the JWT
2. Loads the resource by ID
3. Verifies `resource.userId === jwt.sub`
4. Returns 404 if not found or not owned (no information leak)

## 7. Error Contract

### Stable error envelope

All mobile API errors return a consistent JSON shape:

```typescript
interface MobileApiError {
  error: {
    code: MobileErrorCode
    message: string  // human-readable, safe to display
    details?: Record<string, unknown>  // optional field-level validation details
    requestId: string  // for support correlation
  }
}

type MobileErrorCode =
  | 'AUTH_REQUIRED'           // 401 — no/invalid token
  | 'AUTH_EXPIRED'             // 401 — access token expired (client should refresh)
  | 'AUTH_REFRESH_INVALID'     // 401 — refresh token invalid/expired/revoked
  | 'FORBIDDEN'                // 403 — authenticated but not authorized
  | 'NOT_FOUND'                // 404 — resource doesn't exist or not owned
  | 'VALIDATION_ERROR'         // 400 — request body invalid
  | 'CONFLICT'                 // 409 — idempotency conflict
  | 'RATE_LIMITED'             // 429 — too many requests
  | 'SERVER_ERROR'             // 500 — unexpected server failure
  | 'SERVICE_UNAVAILABLE'      // 503 — database unreachable
```

## 8. API Versioning Strategy

### Version header

```
X-Wayfinder-API-Version: 1
```

The server accepts the header (defaulting to `1` if absent) and routes to the corresponding DTO mapper.

### Breaking change policy

- **Breaking change**: any change to a DTO field name, type, or removal; or a change to auth semantics.
- **Non-breaking change**: adding a new optional field to a response DTO; adding a new endpoint.

### Backward compatibility

- The server supports the previous API version for **90 days** after a breaking change.
- During that window, both `X-Wayfinder-API-Version: 1` and `X-Wayfinder-API-Version: 2` are accepted.
- After 90 days, v1 requests return `400 VALIDATION_ERROR` with `message: "API version 1 is no longer supported"`.

### Deprecation policy

- Deprecated endpoints/fields include a `Deprecation: true` flag in the response header: `Sunset: <date>`.
- The Android client checks the `X-Wayfinder-Min-Client-Version` response header. If the client version is below the minimum, it displays an upgrade prompt.

### Minimum supported client version

The server returns:
```
X-Wayfinder-Min-Client-Version: 1.0.0
```

The Android client compares its build version against this. If below minimum, it refuses to make further requests and prompts the user to update.

## 9. Contract Publication Strategy

### Authoritative source

The **server** (`pectoraux/wayfinder`) is the single source of truth for the mobile API contract.

### Mechanism: TypeScript DTO definitions + generated OpenAPI

1. **Define DTOs** as TypeScript interfaces in `src/lib/mobile-contract/` (a new directory).
2. **Generate OpenAPI 3.1 spec** from the DTOs using `zod-to-openapi` or a similar tool.
3. **Publish the OpenAPI spec** at `GET /api/mobile/contract` (public, no auth).
4. **The Android repo** consumes the published OpenAPI spec to generate Kotlin data classes using a code generator (e.g., `openapi-generator`).

### No manual duplication

- DTOs are defined **once** in TypeScript.
- OpenAPI is **generated**, not hand-written.
- Kotlin models are **generated**, not hand-written.
- The Android repo does NOT maintain a parallel contract.

### Validation

- The server validates incoming requests against the DTOs (using zod schemas derived from the same definitions).
- The Android client validates responses against the generated Kotlin models.
- Drift is structurally impossible — both sides are generated from the same source.

## 10. Separate-Repository ADR

### ADR: Android lives in `pectoraux/wayfinder-android`

**Date**: 2026-08-21
**Status**: Proposed (not yet created)

### Context

The Wayfinder web application lives in `pectoraux/wayfinder` (Next.js + TypeScript + Prisma + Vercel). A mobile (Android) client is needed for P4.1-B / P4.2 BLE.

### Decision

Android will live in a **separate repository**: `pectoraux/wayfinder-android`.

### Rationale

1. **Independent native toolchain.** Android uses Gradle + Kotlin + Android SDK + emulator CI. The web repo uses Bun + Next.js + Vercel. Combining them creates a monorepo with two unrelated build systems and no shared tooling infrastructure.

2. **Independent release cadence.** Web deploys on every push to `main` via Vercel. Android requires APK signing, Play Store review, and versioned SDK levels. Coupling releases adds coordination overhead with no benefit.

3. **Separate CI.** Android CI requires emulator boot, APK installation, instrumentation tests. Web CI requires lint + vitest + Vercel build. The CI matrices are completely disjoint.

4. **Mobile-only capabilities.** P4.2 BLE capabilities (BluetoothManager, GATT, device discovery) are inherently mobile-only. Putting them in the web repo pollutes it with dead code.

5. **Thin-client boundary.** The Android app is a pure API consumer. It contains no intelligence. Keeping it in a separate repo physically enforces this boundary — there is no shared code to accidentally couple.

### What is intentionally NOT shared

| Intelligence | Location | Shared with Android? |
|---|---|---|
| Strategy engine (`buildStrategy`) | `src/lib/strategy/index.ts` | NO |
| Decision Graph (`buildDecisionGraph`) | `src/lib/strategy/decision-graph.ts` | NO |
| Policy engine (`resolveRuntimePolicy`) | `src/lib/policy/runtime-resolver.ts` | NO |
| Knowledge base (`src/lib/knowledge/`) | `src/lib/knowledge/` | NO |
| Prisma access (`src/lib/db.ts`) | `src/lib/db.ts` | NO |
| Outcome evaluator (`evaluateActionOutcomeN07`, etc.) | `src/lib/strategy/outcome-intelligence.ts` | NO |
| Profile validation | `src/lib/domain/profile-validation.ts` | NO |
| Replay + verification | `src/lib/strategy/replay.ts` | NO |
| Expected outcome creation | `src/lib/strategy/outcome-intelligence.ts` | NO |
| Graph validation | `src/lib/strategy/outcome-intelligence.ts` | NO |

### What IS shared

- The **OpenAPI contract** (published by the server, consumed by Android via code generation).
- The **authentication semantics** (JWT format, refresh token protocol).
- The **error envelope** (defined in the contract).

### Consequences

- Two repositories to maintain.
- Contract drift risk mitigated by generated OpenAPI + minimum client version header.
- No language-level code sharing (TypeScript server, Kotlin client).
- BLE code is isolated to the Android repo.

## 13. Security Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Stolen access token | Medium | 15-min expiry limits replay window |
| Stolen refresh token | High | Rotation (single-use) + DB revocation + 30-day expiry |
| Token storage on device | High | Android Keystore (hardware-backed on supported devices) |
| Brute-force login | Medium | Rate limiting on `/api/auth/credentials` (per-IP + per-email) |
| Credential stuffing | Medium | Rate limiting + bcrypt verification (existing) |
| JWT secret compromise | Critical | Separate `MOBILE_JWT_SECRET` env var; rotatable without affecting web sessions |
| OpenAPI spec leaks internal structure | Low | DTOs are explicit projections — internal types are not exposed |
| Cross-user resource access | Critical | Per-request ownership verification (Section 6) |
| Mobile client submits forged predictions | High | Server ignores all predicted* fields in outcome submissions (N0.7 invariant) |
| Mobile client claims EXTERNAL_VERIFICATION | High | `validateProvenance(isClientSubmission=true)` rejects (N0.7 invariant) |

---

## 14. Migration Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Adding mobile auth breaks web NextAuth | High | Mobile auth is additive — new endpoints, new `MOBILE_JWT_SECRET`. Web NextAuth config is untouched. |
| New `MobileSession` Prisma model requires DB migration | Low | Additive migration (new table, no existing data affected). CI already runs `prisma db push`. |
| OpenAPI generation adds build complexity | Low | Use `zod-to-openapi` (already in the TypeScript ecosystem). Spec is generated at build time, published at `/api/mobile/contract`. |
| Android client version fragmentation | Medium | `X-Wayfinder-Min-Client-Version` header + upgrade prompt |
| Existing API routes need DTO wrappers | Medium | Phase the DTO boundary in — start with the 12 mobile-facing routes. Web routes can adopt DTOs incrementally. |
| Rate limiting not currently implemented | Medium | Add a simple in-memory rate limiter for `/api/auth/credentials` in P4.0. Production rate limiting (Redis) is a future infrastructure task. |

```
                 │                                     │
          Web Client                            Android Client
          (existing)                            (pectoraux/wayfinder-android)
                 │                                     │

          cookie auth                           + refresh rotation
                 │                                     │
```

**No second intelligence engine. No second graph. No second provenance system. No Android-side strategy generation. No BLE-side reasoning.**

P4.0 is complete as an architecture document. The mobile boundary is explicit enough that a future Android engineer can implement against it without reading or reproducing the server's intelligence internals.
